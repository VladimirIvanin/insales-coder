# Проверка и границы результата

Отсутствие команды liquid/sass в PATH ещё не означает отсутствие библиотеки: при наличии Ruby отдельно проверь `ruby -e 'require "liquid"'` и `ruby -e 'require "sassc"'`, а для Node — установленные modules через require.resolve. Не скачивай пакет через npx --yes в режиме без установки. Для SCSS фиксируй название и версию компилятора, настоящие mixins темы или диагностические заглушки. Ruby Sass и Dart Sass не проверяют совместимость с SassC/LibSass. Если доступен только другой компилятор, его успех оставляет платформенную сборку непроверенной; отдельно сверяй используемые CSS-выражения с [памяткой SassC](sassc-compatibility.md). Успешный stub также не подтверждает сборку платформой.

Сохраняй exit code самой проверяемой команды. При pipeline с tee используй pipefail/PIPESTATUS либо subprocess с отдельными stdout/stderr; echo $? после tee относится к tee. Различай failed проверки и blocked из-за отсутствующего компилятора/контекста.

**Офлайн.** После создания или изменения `info.json` запусти скрипт из фактического каталога установленного скилла, а не из предполагаемого cwd проекта:

```bash
node "$SKILL_DIR/scripts/validate-info-json.mjs" --context custom "$WIDGET_DIR"
node "$SKILL_DIR/scripts/validate-settings-form.mjs" "$WIDGET_DIR"
```

Задай `SKILL_DIR` по расположению прочитанного `SKILL.md`, а `WIDGET_DIR` — каталог проверяемого виджета; для системного пакета выбери `--context system`, известную целевую локаль можно передать через `--locale`. Это структурные проверки JSON, а не подтверждение установки, существования handles или работы витрины. Для непустого `snippet.js` при наличии Node выполни `node --check "$WIDGET_DIR/snippet.js"` целиком. SCSS и Liquid проверяй доступными инструментами (SCSS платформы использует SassC/LibSass); если нужного инструмента нет, явно назови непроведённую проверку. Используй примеры из скилла и данные своей задачи для существенных ветвей: пустые данные, варианты, отсутствие фото. Не выдавай DOM-fixtures за интеграцию магазина. В отчёте укажи команду/действие, результат и его границы; чтение кода не является запуском синтаксической проверки. Не подавляй ошибки через `|| true` или безусловный success. Непроведённые проверки перечисли отдельно.

**При доступной витрине/редакторе.** Проверь выбранные функции действием, сохранение настроек и повторное открытие. Для шапки используй матрицу из профильного справочника; для карточки — варианты, наличие описания, несколько/одно/нет фото. Проверь быстрый путь «сменить вариант → ввести количество → добавить» и результат в корзине, а не только уведомление. После перерисовки компоненты должны работать без удвоения обработчиков. Используй существующие товары; не создавай их без запроса пользователя.

При визуальной проверке учитывай настоящие стили темы, `my-layout`, шрифты и вложенность `.layout__content`. Сначала дождись стабильного состояния страницы; промежуточный screenshot и отсутствие горизонтального overflow не доказывают ни поломку, ни исправность раскладки. Отличия оформления отделяй от функциональных дефектов. Перечисли, что проверено, что пока нет и почему; отсутствие MCP само по себе не является ошибкой готового офлайн-пакета.


## Проверка поведения до отчёта

Для собственного JS исполни основной сценарий с разметкой, полученной из Liquid и начальных данных: добавление обработчиков к отсутствующим узлам не реализует функцию. Сопоставь результат каждого действия с обещанием интерфейса, включая связанную подпись и обратное действие. Повтори initializer на том же корне после действия: событие не должно срабатывать несколько раз, а производный текст — накапливать фрагменты предыдущего вывода. Затем проверь независимый второй экземпляр и необходимые переходы между страницами/перезагрузку. Методика состояния и cleanup — в [runtime](runtime.md). Без среды исполнения эти проверки остаются непроведёнными.

# Перенос страницы прототипа в виджеты

Этот маршрут нужен для страницы из нескольких секций. Он помогает определить состав и контракты переноса; реализации отдельных функций выбирай по задаче. Готовые пакеты скилла используй для типичных механизмов платформы, а не как обязательные шаблоны каждой секции.

При доступном браузере посмотри референс на широкой и узкой ширине; без него используй исходники и скриншоты, а визуальную проверку отметь как непроведённую. Точное совпадение оформления требуется, когда оно задано задачей.

## Состав страницы

Сначала проследи выполнение нужного маршрута прототипа: основную функцию, вызываемые ею функции и подключённые скрипты, которые меняют страницу. Статический HTML и названия файлов могут не отражать весь состав. Зафиксируй каждую самостоятельную секцию, её источник контента и действия пользователя до начала реализации. Не подменяй этот перечень привычной структурой интернет-магазина.

Сопоставь секции с пакетами и размещениями. Если одна секция объединяет несколько функций, это не причина потерять одну из них. Для каждой секции свяжи исходные контент и действия с их потребителями в пакете: Liquid, данные, JS и видимый результат. Название пакета и наличие заголовка не подтверждают перенос функций секции. В итоговом manifest указывай фактические каталоги, типы, порядок и привязки. Перед завершением сравни его с исходным перечнем: отсутствие секции должно быть явно объяснено, а не скрыто успешными проверками остальных пакетов.

## Контракты платформы

Отдели демонстрационные данные и маршруты от механизмов InSales. Товары получай через product-настройки или коллекции; поля и глобальные объекты проверяй по [Liquid](../insales-liquid/reference.md). Для пустой product-настройки проверяй наличие `product.id`: пустая строка в Liquid истинна. Данные выбранной сущности должны давать её актуальные URL, цену и варианты. Неподтверждённый глобальный поиск по handle не заменяет привязку товара.

Переводи переходы в URL существующих сущностей или редактируемые ссылки. Произвольный параметр запроса прототипа не создаёт фильтр каталога. Если целевой контент ещё не создан, сохрани предоставленные материалы в настройках или блоках и обозначь недостающую привязку; не скрывай раздел за вымышленным handle.

Тип данных виджета, категория галереи и место размещения — разные свойства. Выбирай их по [архитектуре](reference.md#infojson). Для повторяемого редакционного контента используй блоки и начальные данные; для данных каталога — сущности магазина. Число или сложность визуальных элементов сами по себе не требуют `BlockListWidgetType`.

`snippet.liquid`, `snippet.js`, SCSS и настройки должны описывать один контракт. Платформа создаёт внешнюю `.layout` и вставляет JS без Liquid-рендера. Передавай значения в JS через разметку и читай их с того элемента, на котором они выведены; внешний корень виджета и внутренний элемент секции не взаимозаменяемы. Не рассчитывай на дополнительный проход шаблонизатора или неподтверждённые фильтры.

## Поведение и оформление

Для интерактивной функции определи действие пользователя, изменение состояния и видимый результат. Переноси эту связь целиком: разметка с `data-*` сама по себе не создаёт обработчик. Выбор области хранения и повторная инициализация описаны в [runtime](runtime.md#срок-жизни-состояния). При переходе от SPA к серверной навигации проверь, какие исходные обещания сохраняются, а какие требуют согласованного изменения поведения.

Сохраняй зависимости геометрии: относительные координаты, кадрирование, позиционирование и связанные элементы должны использовать одну систему отсчёта. После изменения ширины проверяй доступность действий и соответствие связанных элементов, а не только отсутствие overflow.

Учитывай настоящий HTML редактируемого контента: rich-text может содержать абзацы и другую вложенную разметку. Общие правила для абзацев секции не должны переопределять типографику вложенного заголовка. Проверяй результат с исходным и изменённым через редактор содержимым.

## Проверка переноса

Проверяй результат по исходным требованиям, а не по выбранной реализации. Для каждой секции нужен наблюдаемый признак присутствия; для интерактивной функции — выполненное действие и проверенный результат. Пустые привязки и второй экземпляр позволяют обнаружить ошибки, незаметные на заполненной одиночной секции.

Синтаксическая проверка не обнаруживает необъявленные переменные, неверный DOM-корень или отсутствие поведения. В доступном runtime запусти initializer и основной сценарий, затем проверь повторную инициализацию. Без runtime перечисли эти проверки как непроведённые. При доступном магазине проверь сохранение настроек, реальные данные, действия и устойчивую раскладку; DOM-fixtures не заменяют эту проверку.

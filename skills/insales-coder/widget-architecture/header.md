# Обычная шапка: данные и состояния

Читай при создании или переносе шапки. Начни с выбранных пользователем функций и композиции: зоны логотипа, поиска, действий и каталога, поведение на узком экране. Магазин, MCP и браузер полезны для дополнительной проверки, но не нужны для подготовки и проверки исходников. Точное повторение стиля нужно, когда оно заказано; ниже один возможный интерфейс, а не стандарт оформления.

`info.json`: для штатной категории шапок используй `widget_category_handle: "headers"`, для размещения — `widget_list_kinds: ["header"]`; это разные справочники. Наличие категории в целевом каталоге проверяется отдельно.

## Небольшой адаптированный пример

[Liquid](examples/header/snippet.liquid), [JS](examples/header/snippet.js), [SCSS](examples/header/snippet.scss) образуют пример содержимого трёх файлов виджета, а не готовый установочный пакет. Добавь metadata/settings по [архитектуре](reference.md) и [настройкам](settings-reference.md). Прямые зависимости `info.json`:

```json
{ "libraries": ["jquery", "commonjs_v2", "body-scroll-lock"] }
```

В `settings_form.json` добавь поле `{"name":"logo","type":"file","label":"{{ messages.logo }}"}` в принятую в виджете группу; `settings_data.json`: `{"logo":null}`. Без загруженного файла используется `{% default_logo %}`. В `messages.json` нужны ключи `logo`, `catalog`, `subcategories`, `search`, `compare`, `favorites`, `cart`, `close`, например `{"ru":{"catalog":"Каталог","search":"Поиск"},"en":{"catalog":"Catalog","search":"Search"}}` (корень — локаль, внутри — ключи сообщений). Подписи в форме используют `messages`, в Liquid — `widget_messages`. Логотип получает реальный URL из file-поля; путь локального файла не является значением для витрины.

Пример берёт три уровня настоящих `collections.root_category.subcollections`; последний уровень остаётся ссылкой на категорию с её полным содержимым. Переход и раскрытие разделены: ссылка ведёт в категорию, `<summary>` раскрывает дочерние пункты клавиатурой, мышью и touch. На desktop ветви раскрываются в потоке, ряд прокручивается горизонтально. Это намеренный простой вариант без hover-меню и «Ещё». Для другого дизайна можно выбрать [InsalesCutList](../libraries/navigation-filters.md), flyout с проверкой границ viewport или выбранное `linklists[widget_settings.menu_handle].links` с полем типа `navigation`. Не подменяй данные каталога статическими названиями. При добавлении кеша включай зависимости каталога/меню и настроек по [контракту кеша](../liquid-widget-cache-keys/reference.md).

`data-navigation` обозначает корень, `data-navigation-item` — пункт, `data-navigation-link="URL"` — ссылку, `data-navigation-submenu` — вложенный список. Проверенный common.js добавляет `.is-current` ссылке и предкам по точному совпадению `location.pathname` со значением `data-navigation-link`, затем ставит `data-navigation-inited`. Эти атрибуты **не открывают подменю**. В примере собственная локальная проверка pathname также ставит `aria-current="page"` и работает при повторном запуске JS; dropdown-поведения common.js не предполагается.

## Поиск и действия

Поиск остаётся видимым в обеих раскладках: одна форма, `name="q"`, скрытый `lang`, `data-search-field` и `data-search-result` в той же форме. Отправка `/search` работает и без живой выдачи. `commonjs_v2` обслуживает AjaxSearch; не добавляй второй обработчик запросов и не меняй глобальный `AjaxSearch.setConfig` ради одного экземпляра.

Штатная выдача использует `.ajax-search-results`, `.ajax-search-item`, `.ajax-search-link`, подсветку `.ajax_search-marked`; класс `.is-show` получает **форма** при наличии результатов. SCSS должен оформить контейнер, ограничить высоту, разрешить scroll и обеспечить доступ к ссылкам при узкой ширине. При пустом/слишком коротком запросе стандартный шаблон пуст, `.is-show` снимается: это не отдельное сообщение «Ничего не найдено». Если дизайн требует loading/empty/error и полноценный combobox с управлением стрелками, реализуй эти состояния отдельно по [API поиска](../commonjs-widget/js-api.md), не объявляй их автоматическими свойствами data-атрибутов.

common.js обновляет `data-cart-positions-count`, `data-ui-favorites-counter`, `data-compare-counter` и классы пустоты `.cart-empty`, `.favorites-empty`, `.compare-empty`. Скрывай пустой **бейдж**, оставляя ссылку доступной. Начальные пустые классы предотвращают мелькание нулей. Для корзины `cart-empty` обновляется **на самом `[data-cart-positions-count]`**, не на родительской ссылке. Начальный класс и правило скрытия привязывай к этому же бейджу:

```liquid
<a href="{{ cart_url }}">
  {{ widget_messages.cart | escape }}
  <span class="header-cart-count cart-empty" data-cart-positions-count>0</span>
</a>
```

```scss
.header-cart-count.cart-empty { display: none; }
```

Если навсегда поставить `cart-empty` на ссылку и скрывать её дочерний счётчик по этому классу, бейдж останется невидимым после наполнения корзины. Проверь оба перехода `0 → 1 → 0`, включая computed visibility, а не только текст узла.

Доступность функции решает Liquid: `account.show_cart?`, `settings.favorite_enabled == true`, `settings.compare_enabled == null or settings.compare_enabled`. Настройки скрытия конкретного виджета добавляй, если они нужны заданию; не создавай второе клиентское хранилище счётчиков. После изменений корзины данные поступают из штатных событий common.js; обычному счётчику не нужен собственный polling.

## Мобильная панель и жизненный цикл

Пример использует нативный `<dialog>.showModal()` для модальности/фокуса и библиотеку `bodyScrollLock` для прокручиваемого `.recipe-header__panel`. Поддержку dialog сопоставь с целевыми браузерами; альтернативный вариант — [MicroModal](../libraries/overlays.md) с тем же контрактом состояний. Кнопка, backdrop, переход по ссылке, Escape (`cancel`) и смена breakpoint сходятся в `close()`. Он снимает lock и `aria-expanded`, возвращает фокус при обычном закрытии; при resize фокус переходит на видимый логотип. Внутренний panel прокручивается, высота `100dvh` имеет fallback `100vh`. Не пиши `body.style.overflow = 'auto'`: это может разблокировать чужую панель.

JS инициализирует каждый элемент `$widget` отдельно, хранит cleanup на его корне и вызывает его перед повторным запуском. Наблюдатель освобождает обработчики и lock при удалении корня или замене его содержимого. Вставка новой разметки требует запуска initializer платформой или адаптера по [общему lifecycle](runtime.md); сам наблюдатель пример заново не создаёт. При подключении общего runtime перенеси этот cleanup в его disposer, чтобы не держать два наблюдателя. В common.js обработчик виджетов принимает `update_widget:insales:widgets` и обновляет Cart/Favorites/Compare/меню после перерисовки; это событие не является подтверждённым событием удаления. Общие API common.js не уничтожай из cleanup отдельной шапки.

## Проверка выбранных функций

Офлайн используй доступные инструменты для проверки синтаксиса JS, компиляции SCSS и Liquid на fixtures каталога и flags. Если есть DOM harness, проверь открытие/закрытие, cleanup и два экземпляра. Непроведённые проверки перечисли с причиной. Разделяй заглушки и фактический runtime: fixtures не подтверждают серверный поиск, корзину или редактор. Сохрани команды, результат и ограничения. Этого достаточно для исходников без подключённого магазина.

При доступной витрине добавь сценарии на 390/768/1440 px: длинные категории и логотип, все выбранные уровни, горизонтальный overflow, desktop mouse/touch, поиск с результатами/без результатов, пустые/непустые/выключенные controls. Для панели проверь Escape, Tab/Shift+Tab, возврат фокуса, scroll, resize при открытии; для lifecycle — rerender/settings, удаление открытой панели и независимость двух экземпляров. Оцени читаемость и доступность действий; сравнение пикселей нужно по заданию. Sticky, мегаменю с фото, языки, телефон, видео/slider и пересчёт visualViewport добавляй только при соответствующей задаче.

Контракты поиска, счётчиков и меню описаны в [разметке common.js](../commonjs-widget/markup.md) и [JS API](../commonjs-widget/js-api.md). Пример использует эти справочники и включённые в скилл файлы; отдельная копия исходников платформы ему не требуется.

# InSales Coder

Разрабатывай по доступным исходникам, данным и справочникам. Скилл работает **без MCP и доступа к магазину**: их отсутствие не блокирует подготовку полного пакета. Читай только разделы, нужные для задачи: выбери один подходящий пример и открывай дополнительные справочники по используемым механизмам.

## Основа нового виджета

- Для нового gen4-пакета явно указывай `generation: 4`. Системный или кастомный контекст определяется владельцем при установке, а не одним префиксом handle. У нового кастомного виджета обычно опускают `sku`, чтобы его сгенерировала платформа; подробности — [проверка info.json](widget-architecture/info-json-validation.md).
- `settings_form.json` поколения 4 содержит вкладки `content` и `design`: массивы групп с массивами `items`. Минимальная форма — `{"content":[],"design":[]}`. `name` — идентификатор поля, `label` — подпись, defaults хранятся в `settings_data.json`. Текст с HTML делай `rich-text`; без разметки подходит `text`.
- Тексты, подписи, ссылки и изображения делай редактируемыми через настройки/блоки; товары, цены и варианты получай из каталога. У каждой настройки должно быть назначение в Liquid, JS, SCSS или механизмах платформы. Отсутствие прямого обращения в Liquid не доказывает, что настройка лишняя.
- При файловом импорте исполняемые файлы называются `snippet.liquid`, `snippet.scss` и `snippet.js`. Произвольные имена вроде `widget.liquid` не подхватываются автоматически. До завершения сверяй имена файлов и непустую разметку пакета; успех JSON-валидаторов этого не подтверждает.
- Для статических секций достаточно Liquid/CSS: `snippet.js` необязателен. Локальные события и внешние ресурсы требуют разных механизмов — [выбор поведения](widget-architecture/runtime.md). В новом JS используй `const`/`let`. Не добавляй наблюдение за удалением DOM: перед удалением или заменой компонента владелец явно вызывает cleanup.
- При сборке страницы самостоятельной секции соответствует отдельный экземпляр. Ненужные размещения снимай с виджетлиста, а не скрывай через обрезку массива или пустой вывод.
- Объявляй непосредственно используемые библиотеки в своём `info.json`; не полагайся на соседние секции. Поля Liquid и API сверяй со справочником, доступными исходниками или документацией, не придумывай их.
- Не угадывай связанные handles по месту размещения: у шапки категория `headers`, а размещение `header`. Примеры категорий и границы проверки — в [архитектуре](widget-architecture/reference.md#infojson).
- Для ветвления Liquid используй `elsif`, а не `elif`. Liquid не поддерживает комментарии Twig/Jinja `{# … #}`: они попадут в текст страницы. Используй `{% comment %}…{% endcomment %}`; успешный parse сам по себе не обнаруживает чужой синтаксис, оставшийся обычным текстом.
- Сохраняй читаемость и семантику исходников, особенно пробелы Liquid. Скилл не требует одного форматтера, одинаковых кавычек или JS-архитектуры.

## Проверки по доступной среде

Отсутствие команды liquid/sass в PATH ещё не означает отсутствие библиотеки: при наличии Ruby отдельно проверь `ruby -e 'require "liquid"'` и `ruby -e 'require "sassc"'`, а для Node — установленные modules через require.resolve. Не скачивай пакет через npx --yes в режиме без установки. Для SCSS различай настоящие mixins темы, диагностическую заглушку и другой Sass-компилятор; успешный stub не подтверждает сборку платформой.

Сохраняй exit code самой проверяемой команды. При pipeline с tee используй pipefail/PIPESTATUS либо subprocess с отдельными stdout/stderr; echo $? после tee относится к tee. Различай failed проверки и blocked из-за отсутствующего компилятора/контекста.

**Офлайн.** После создания или изменения `info.json` запусти скрипт из фактического каталога установленного скилла, а не из предполагаемого cwd проекта:

```bash
node "$SKILL_DIR/scripts/validate-info-json.mjs" --context custom "$WIDGET_DIR"
node "$SKILL_DIR/scripts/validate-settings-form.mjs" "$WIDGET_DIR"
```

Задай `SKILL_DIR` по расположению прочитанного `SKILL.md`, а `WIDGET_DIR` — каталог проверяемого виджета; для системного пакета выбери `--context system`, известную целевую локаль можно передать через `--locale`. Это структурные проверки JSON, а не подтверждение установки, существования handles или работы витрины. Для непустого `snippet.js` при наличии Node выполни `node --check "$WIDGET_DIR/snippet.js"` целиком. SCSS и Liquid проверяй доступными инструментами (SCSS платформы использует SassC/LibSass); если нужного инструмента нет, явно назови непроведённую проверку. Используй примеры из скилла и данные своей задачи для существенных ветвей: пустые данные, варианты, отсутствие фото. Не выдавай DOM-fixtures за интеграцию магазина. В отчёте укажи команду/действие, результат и его границы; чтение кода не является запуском синтаксической проверки. Не подавляй ошибки через `|| true` или безусловный success. Непроведённые проверки перечисли отдельно.

**Перенос прототипа.** Для страницы из нескольких секций начни с [маршрута переноса страницы](widget-architecture/prototype-page.md). Сначала выдели нужные секции и функции. Растровые file-URL выводи через `image_url` с подходящим размером; для SVG используй исходный URL. Это не заменяет загрузку файла и привязку AccountFile. Если браузер доступен, посмотри референс на широкой и узкой ширине: HTML не передаёт полностью композицию. Без браузера используй предоставленные файлы/скриншоты, продолжай реализацию и обозначь визуальную проверку как непроведённую. Точное совпадение шрифтов, цветов и отступов требуется только по запросу; обычные критерии — читаемость, доступность действий и адаптивность.

**При доступной витрине/редакторе.** Проверь выбранные функции действием, сохранение настроек и повторное открытие. Для шапки используй матрицу из профильного справочника; для карточки — варианты, наличие описания, несколько/одно/нет фото. Проверь быстрый путь «сменить вариант → ввести количество → добавить» и результат в корзине, а не только уведомление. После перерисовки компоненты должны работать без удвоения обработчиков. Используй существующие товары; не создавай их без запроса пользователя.

При визуальной проверке учитывай настоящие стили темы, `my-layout`, шрифты и вложенность `.layout__content`. Сначала дождись стабильного состояния страницы; промежуточный screenshot и отсутствие горизонтального overflow не доказывают ни поломку, ни исправность раскладки. Отличия оформления отделяй от функциональных дефектов. Перечисли, что проверено, что пока нет и почему; отсутствие MCP само по себе не является ошибкой готового офлайн-пакета.

## Настройки и изображения

Для старых `layout-pt`/`layout-pb` при мобильном коэффициенте `4` используй `unit: "vw"`; для `rem`/`px` нужен явный коэффициент `(0, 1]` на корне. Для точных отступов удобнее `layout-pt-desktop-px`, `layout-pb-desktop-px`, `layout-pt-mobile-px`, `layout-pb-mobile-px` с `unit: "px"` и числовыми defaults: мобильные пиксельные значения не умножаются, без них используются десктопные. Подробности — [Core CSS](widget-architecture/core-css-reference.md).

Без магазина приложи локальные изображения и карту «файл → настройка», оставив незагруженные file-поля пустыми. С доступом к магазину загрузи их в «Файлы», выбери в редакторе/API и проверь сохранённое значение AccountFile; его форма описана в [runtime.md](widget-architecture/runtime.md). Не подставляй постоянную ссылку сайта-референса вместо незаполненного поля. Если предмет должен быть на прозрачном фоне, проверь фактический альфа-канал и края, а не расширение файла.

## Если доступен MCP

Это дополнительный способ установки и проверки. Перед изменением существующего виджета прочитай актуальный код магазина. Для больших исходников настрой абсолютный `INSALES_MCP_WIDGET_SOURCE_ROOT` и передавай относительные пути в `source_files`, включая повторы после конфликта ревизии. Сверь SHA-256 черновика с локальными файлами; после `apply_change` прочитай сохранённый код и сравни его. Если чтение ещё показывает старую версию, повтори после короткой задержки.

Для изображений используй доступный `propose_theme_image_upload(destination=account_file)` и затем `apply_change`; проверь привязку через чтение темы. Ошибка разрешённого каталога загрузки и способы её исправления — в [editable-theme.md](widget-architecture/editable-theme.md). MCP-сохранение или аудит состава секций не заменяют проверку поведения.
